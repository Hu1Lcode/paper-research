Sol-Engine：把视频 diffusion 推理加速做成agent 可执行的工程

它不是又一个模型，而是一套效率型推理框架：建立在 SGLang 的 multimodal_gen runtime 之上，把 cache、稀疏注意力、token 剪枝、量化、kernel 融合五类技术组织成 agentic 加速栈，为每个「模型 × 硬件 × 服务配置」组合找到各自的加速线。单模型 2.17×–5.03×；组合式 MiniMax-H3 Super Acceleration 达 22.2×（5 s）/ 27.7×（10 s）；Sol-H3 在 8×B300 上把 5 秒带音频视频压到 1.653 s——比实时播放更快。

①

一句话与它真正的创新点

加速方法本身多数是"公开知识的组合"；这个项目的差异化在于把加速工程本身交给 agent，并用严格的分母与质量门约束每一个结论。

一句话

最有效的加速配方是 instance-specific 的：换模型、换分辨率与时长、换 GPU，配方就失效。手工性能工程太贵，于是 Sol-Engine 把五类通用技术拆成带契约的 config manifest，让并行 skill agent 各自优化一种技术、agent integrator 合成全局加速栈、human validator 把关质量。

5加速技术族（cache / 量化 / 融合 / 稀疏注意力 / token 剪枝）
11模型加速线，含组合式 Super Acceleration
1.653 sSol-H3：8×B300 上 5 秒带音频视频
56 sSol-H3-Spark：单卡 DGX Spark 出 768p 5 s

痛点：三处 heterogeneity 叠出巨大的调参空间

维度差异体现在哪
模型架构、数值敏感度、attention 的集中程度各不相同 —— 同一个稀疏度在 A 模型可用，在 B 模型就掉画质
推理配置空间/时间分辨率与视频时长差异极大（768p 5 s 与 4K 20 s 的最优配方完全不同）
硬件显存层级、支持的数值格式（NVFP4 需 Blackwell）、kernel 吞吐都不同（从 A100 到 B300、从 RTX 4090 到 DGX Spark）

结论：需要的是"面向实例的自动优化流程"，而不是一套固定超参。

① 三类冗余的完整切分

算法层（跨去噪步）、模型层（长序列 token 与 attention）、kernel 层（GEMM 周围的 memory-bound glue），五类技术正好覆盖三层。

② Agent-native 编排

master orchestrator + 每技术一个 executor 子 agent + integrator 合成；安装与调优都不是"照着脚本敲"，而是把 goal 交给 Codex / Claude Code。

③ 可审计的数字

baseline 与同拓扑 control 是一等公民；LPIPS + VLM 视觉门 + authenticity check 三重质量门，防止"空转优化"报出假 speedup。

每一类都配了"设计空间"（搜索什么）与"已实现条目"（仓库里真有哪些），并且都标注了在哪些模型上用。

③

Sol-Attn：一次 online softmax 里完成路由、稀疏与校正

它解决的问题很具体：既有的 training-free 动态稀疏注意力，要么路由僵硬昂贵，要么"保留/丢弃"太有损。

既有方法的两处缺陷

问题表现
路由刚性/昂贵按 proxy score 取固定比例 top-k → 预算固定；按累积 proxy 概率质量取块 → 预算动态但可能失衡；两者都要计算并物化 proxy 分数，开销不可忽略
keep-or-drop 有损未选中的 block 被整体丢弃，激进稀疏下精度迅速下降

Sol-Attn 的三合一

机制作用
On-the-fly block thresholding在 online softmax 过程中用 block proxy score 与阈值比较，动态且可控的 block 预算
Proxy-score reuse未选中 block 复用 proxy 分数近似其贡献，而不是丢弃 → 近似校正
No routing map无需物化完整 routing map，一次 pass 完成
核心 API（tau 越大，精确计算的 KV block 越少） out = sol_attn( q , k , v , tau=1.0 , thresh_type="exact" )
把 valid text 的 K/V block 钉成精确（64-token block 粒度） out = sol_attn( q , k , v , tau=1.0 , sink_start=0 , sink_tokens=valid_text_tokens )

Config 契约与运行产物

每个优化都是一份 config manifest：id、kind（baseline / patch / control）、runtime、开启技术的环境变量、eval profile。单一 launcher 渲染可复现 run bundle：runs/<timestamp>-<id>/ 含 launch.sh、manifest.resolved.toml、metadata.json 与 outputs/（视频 + benchmark.json，记录实际选中的 backend）。

报告约定

  • speedup 必须写明分母（single-GPU / same-topology / vs-naive），不得静默混用；
  • 计时排除模型加载，取官方验证 prompt 上的中位数，同 seed；
  • 改变浮点归约顺序或 attention 稀疏性的优化，标注为 non–bit-exact。

四个旗舰案例

从"比播放更快"到"单卡一分钟出 768p"，再到把两个模型串成一个 22× 的组合流水线。

案例一 · Sol-H3 on 8×B300：5 秒视频 1.653 s

1×B3005 / 10 / 15 s129.898 / 376.942 / 746.885 s13.745 / 37.813 / 52.260 s9.45× / 9.97× / 14.29×

1344×768、24 FPS、同 prompt 与 seed 20260903、reference-free T2VA + 立体声；Base H3 用 50 scheduler points（49 次 DiT forward），Sol-H3 仅 4 次 DiT forward；数值为 1 次 warmup 后 3 次的中位数，含文本编码 / DiT 去噪 / 音视频 VAE 解码，不含模型加载、编译预热与 MP4 编码。可选 fused MXFP8 把 5 s 档降到 1.472 s；4×/8× 用 Sol-Attn + INT8 QKV / FP8 output transport。

一个 kernel 级细节

每个 block 直接读取自己的 cached slice，省掉两次 index 选择：跨 50 个 block × 4 步，减少约 400 次小 kernel launch，每步避免约 26 GB 显存读取，输出不变。

默认 T2VA 配方要点

  • 常驻 NVFP4 AWQ Qwen 编码 prompt；
  • Draft：H3 + FastH3 VSA DataFree LoRA + W8A8 FP8 DiT，4 次更新 @672×384×124；
  • Draft attention：VSA，90% video sparsity，64-token block，cuDNN BSA 后端；

  • Refine：BF16 LTX-2.5 dev + distilled LoRA 450（strength 0.8），3 次联合音视频更新；
  • Refiner attention：Triton Sol-Attn，step 阈值 1 / 1.25 / 1.5，第一层 dense。

案例三 · H3 Super Acceleration：22.2× / 27.7×

Stage 1 用 4-step H3（896×512、124 帧、24 FPS，LightX2V 四步 LoRA 启动时合并）出 draft；Stage 2 用 LTX-2.5 三步 refine（x2 latent upsampler + 原 VAE 高分辨率首帧条件 + 原 Audio VAE）。实测 768p 5 秒 6.852 s、10 秒 14.931 s，对已发布 SGLang baseline 为 22.2× / 27.7×。

该路径改变了采样轨迹，与 baseline 非 bit-exact；细节/纹理/运动/音频可能有差异——项目页把成对视频摆在页面上让人自行判断。

⑧

局限与注意事项

  • 加速不是无损：改变浮点归约顺序或 attention 稀疏性的优化明确标注 non–bit-exact；H3 Super Acceleration 自述"这不是无损加速，采样路径已改变"；
  • 分母纪律：所有 speedup 都对应明确 baseline（single-GPU / same-topology / vs-naive），计时排除模型加载、取中位数、同 seed，不同分母不可混用；
  • 质量门 ≠ 质量结论：v2 profile 因缺配对 baseline 与感知质量门，主动声明不宣称 speedup、不宣称质量通过；
  • 硬件/后端依赖：NVFP4 需 Blackwell + TransformerEngine（否则回退 BF16）；Sol-Attn 的发布 speedup 基于 CuTe DSL kernel，A100 等回退 Triton reference（正确但非发布口径）；Metal 需 torch.mps.compile_shader；
  • Kernel 限制：Sol-Attn kernel 目前 forward-only，要求 contiguous BF16、BTHD、head dim 128；
  • 仍需人：To-do 里 "agent-native workflow without human-in-the-loop" 尚未完成，论文也把 human validator 列为流程一环；
  • 实现分散在两处：部分 attention / token-prune backend 位于 SGLang 的 multimodal_gen runtime，复现需同时拉上游仓库；search_space/ 是内部仓库导入的快照。
