verl-omni 架构与调用流程

在固定版本的上游依赖之上做的一层扩展：复用 verl 的 Ray 执行、WorkerGroup、AgentLoopManager、 CheckpointEngine 与 Hydra 配置，复用 vLLM-Omni 的推理引擎与扩散 pipeline，自研扩散 / 全模态 RL 的 V1 trainer、worker、diffusion agent loop、reward loop，以及按 (architecture, algorithm) 注册的 pipeline 适配器。核心是一台通用的「采样 → 打分 → 优势 → 更新 → 同步权重」机器，具体模型只是插在注册点上的适配器。

1一层扩展，不是 fork

verl-omni ≠ verl / vllm-omni 的 fork：不改上游，只在其上加扩展层。代码分工是硬约束—— trainer/、workers/、agent_loop/ 保持模型 / 算法无关，模型特有逻辑全部收进 pipelines/<model>_<algo>/。

2V1 的三个结构性改变

① 用 TransferQueue（分布式 KV + 按 key 拉取）替代 v0 的 Ray RPC 传 DataProto； ② 采样与训练解耦：agent loop worker 是 CPU Ray actor，FSDP2 在另一组 NPU 上； ③ ActorRolloutRefWorker 共置 actor / rollout / ref / checkpoint engine，LoRA 模式下 ref 直接复用 actor 的 base 权重。

3流水：训练上一步的同时生成下一步

_submit_batch_to_rollout 在 _sample_batch 之前异步提交下一批 prompt，因此 gen 与 update_actor 重叠；reward 走 streaming 路径，每条样本生成完立即打分， 不阻塞整批。

主调用链 异步 / 跨进程调用（agent loop、HTTP、权重同步） 数据写入 TransferQueue 节点顶部灰字 = 源码位置（标「上游」者位于 site-packages 的 verl / transfer_queue）

五层自上而下：启动层（shell + Hydra + ray.init）→ 编排层（1 CPU 的 DiffusionTaskRunnerV1）→ 训练驱动层（PolicyGradientDiffusionTrainerV1Sync 的 fit 主循环）→ 采样侧 / 训练侧（解耦的两组 Ray actor）→ 数据总线 TransferQueue。左侧虚线是 trainer 与 TQ 之间的 put / sample；右侧虚线是 rollout 轨迹的写回。每个组件框顶部那行灰字标出它所在的文件与行号（路径相对仓库根 /home/wjh/verl-omni）。

调用方向（请求 / 触发） 返回 / 回写 每步循环边界

上半段是一次性初始化（Ray、worker group、vLLM-Omni、agent loop manager、初始权重同步）； 虚线框内是每一步训练循环：feed（提交下一批）→ gen（agent loop + vLLM-Omni + reward）→ train（old_log_prob → advantage → update_actor）→ update_weights。

橙色节点：数据在 TransferQueue 中的两次落地

prompt 行以 status=pending 进入 TQ，轨迹行以 status=success 带着 rollout_log_probs、rm_scores、extra_fields 回来；训练消费完后 kv_clear 清理该批 key，LoRA 增量经 CheckpointEngine 回到推理侧，形成闭环。

关键机制

TransferQueue：V1 的数据中枢

trainer 按 uid 把 prompt 行 put 进 partition_id="train"（验证用 "val"）， 打 status=pending；agent loop 生成完一条轨迹就写回 prompts / responses / rm_scores / rollout_log_probs / extra_fields 与 status=success； trainer 用 ReplayBuffer.sample() 按 global_steps 与 batch 大小拉取，过滤过期样本， 再转 DataProto；一步结束后 tq.kv_clear(...)。V1 强制 transfer_queue.enable=True， 并注入 TRANSFER_QUEUE_ENABLE=1 到 Ray runtime env。

Reward 的两条路径

streaming / async（本例）：无 RM server 或 RM 使用独立资源池，agent loop 每条样本完成时立即发给 reward-loop worker，句柄经 AgentLoopManagerTQ 传入；trainer 侧 use_rm=False，不重复计算。
colocated：RM 与 actor 共置时，trainer 在采样后调用 compute_rm_score。 两个子奖励 required=true，任一失败直接报错而不是静默记 0。

sync 模式的生命周期 hooks

on_init_end → update_weights(0)，保证第一次 rollout 就用当前策略； on_sample_end → sleep_replicas() 释放 rollout 显存给 actor 更新让路； on_step_end → update_weights(step) 唤醒 replica 并推送 LoRA 增量。 增量到引擎模块的映射在 pipelines/minimax_h3_flow_grpo/weight_sync.py 的 map_lora_update_to_engine。

采样与训练解耦

Agent loop worker 不在 GPU 上：它只做 tokenize、向 vLLM-Omni 发 HTTP、收集 artifact、调用 reward、写 TQ。 actor 的 FSDP2 进程在另一组 NPU 上，两侧只通过 TransferQueue 与权重同步交互，因此 16 卡切成 4 个 TP=4 的 rollout replica 之后仍有 4 个 agent loop worker 与之匹配。
